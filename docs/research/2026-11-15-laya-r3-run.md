# Laya r3: the run, and why it does not pass the gate

**Measured:** 2026-11-15, 19:56–20:37 local (41 min wall time).
**Plan:** [`2026-11-15-laya-r3-retrain.md`](../plans/2026-11-15-laya-r3-retrain.md).
**Artifact:** `~/.laya-ft/runs/r3/` (kept for analysis; `published: false`, r2 stays served).

## 1. The "~5 h per run" estimate was wrong by an order of magnitude

The plan carried `~5 h per run` (Decision 4) with nothing measured behind it. Two
timed runs on the existing r2 corpus (`data/train_v2.jsonl`), r2's recipe
(`micro_batch 2 × grad_accum 32`, `soft-ce`, `--device mps`), fitted a line:

| Train items | Wall time |
|---|---|
| 180 (+20 cal +20 eval) | 49.3 s |
| 540 (+60 cal +60 eval) | 105.3 s |

⇒ **≈ 21 s fixed + 0.156 s per item per epoch**, i.e. 0.31 s per micro-batch at
both points (linear, consistent). r2's own artifacts agree: `checkpoint_latest`
(end of epoch 3) at 21:14, final save 21:25.

The real r3 run was slower than that line predicts — **0.25 s per item per epoch**
instead of 0.156 — because the r3 corpus carries longer prompts (the shadow
prompts are long and get truncated to the Laya budget). 3162 train items × 3
epochs took 41 min, not 5 h.

**Consequence:** no packet/resume work is needed. `laya-train` 0.4.2 has no
resume anyway (`save_checkpoint` writes weights, encoder config, tokenizer and
config — no optimizer or scheduler state), and epoch-splitting would not be
equivalent: `CosineAnnealingLR(T_max=optimizer_updates(…, epochs))`,
`sigma_at(epoch, epochs, …)` and `random.Random(seed + epoch)` all depend on the
total epoch count, so three 1-epoch runs give three cosine cycles and a
restarted sigma schedule.

## 2. Corpus (`~/.laya-ft/to_laya_jsonl_v3.py`, new)

| Source | Items | Rows | Weight |
|---|---|---|---|
| Shadow live labels (owner truth) | 253 | 1291 | 5× |
| Golden dev (owner truth) | 85 | 207 | 3× |
| Session train (GLM-5.3 teacher) | 2015 | 2015 | 1× |
| Golden test | — | — | never |
| **Total** | **2379** | **3513** | |

`laya-train` carved 351 items as its calibration slice, leaving 3162 train items.

The corpus script is `~/.laya-ft/to_laya_jsonl_v3.py` (new; `to_laya_jsonl_v2.py`
is untouched). It stays outside this repository by the owner decision of
2026-11-01: `~/.laya-ft` — corpus, labels, golden set and training scripts —
stays local, only the method is documented here. Constants that matter for
reproduction: `SHADOW_REPEAT = 5`, `GOLDEN_REPEAT = 3`, teacher rows 1×,
`LAYA_CONTEXT_BUDGET_TOKENS = 1024`, `CHARS_PER_TOKEN = 3`,
`TRUNCATION_MARKER = "\n[... TRUNCATED ...]\n"`.

The run itself:

```
cd ~/.laya-ft
venv-train/bin/laya-train --data data/train_v3.jsonl --out runs/r3 \
  --base convaiinnovations/laya --epochs 3 --micro-batch 2 --grad-accum 32 \
  --loss soft-ce --label-smoothing 0.05 --device mps
```

Epoch mean losses 1.2305 / 0.3901 / 0.1114. The gate was evaluated with
`golden_eval_v2.py` plus a direct `/classify` sweep against a
`spikes/laya-http/server.py` started on the r3 checkpoint (port 8091, killed
afterwards; the r2 sidecar on 8089 was never touched).

Two parity fixes over the plan's sketch:

- **The queue stores no snippet.** The router sends `lastAssistantSnippet`
  (150 chars) and r2's corpus had it in 85 % of rows. The shadow queue rows have
  no such field, so 38 % of the corpus would have been trained in a format the
  router never sends. The decision log does carry it: joining
  `(queue.logged_at, queue.prompt)` to `input.text` recovered prev/snippet for
  **286 of 286** queue rows (228 with a snippet).
- **Prompt truncation.** `truncatePromptForLaya` (head+tail with the marker,
  budget 1024 tokens × 3 chars − head − context block) is reimplemented in the
  corpus script; 373 rows were truncated. Without it the model would train on
  prompts the router never sends.

Head text and category list are byte-identical to r2 (`data/laya_head_v3.json`
vs `laya_head_v2.json`), so the served head sha256 stays
`5f12495d95d8743a277aa668ad0c8d756f2de1e76b82d80a85b65067e2900883` — verified
against a sidecar started on the r3 checkpoint.

## 3. `continue`: the plan's variant B could not be executed as written

Variant B relabels every `continue` row to the category it would inherit and
drops rows without `prev`. **The inherited category is not in the data:** the
corpora store the previous user *message*, not its category, and the decision
log resolves only 22 of 545 `continue` rows (10 shadow, 12 teacher).

Strictly applied, B would have left the corpus with **zero** `continue`
examples — and gate G2 measures `continue` recall on 25 golden-test items, so it
would have been unpassable by construction.

Owner decision (2026-11-15, same day): relabel where resolvable, keep the rest
as `continue` at **weight 1** (not the 5×/3× owner weight), so the class stays
alive without amplifying the over-prediction r2 showed. `continue` share fell
from 24.5 % (r2) to 14.9 %.

## 4. Gate (evaluated once, golden `test`, n=88 of 92; 4 ambiguous excluded)

| Rule | Threshold | r2 | **r3** | |
|---|---|---|---|---|
| G1 group accuracy | ≥ 53.4 % | 43.2 % | **43.2 %** | FAIL |
| G2 `continue` recall | ≥ 60 % | 27.8 % | **56.0 %** (14/25) | FAIL |
| G3 ECE | ≤ 0.10 | not measured | **0.247** | FAIL |
| G4 live shadow group accuracy | ≥ 30.5 % and ≥ r2 | 22.8 % | not measurable | — |

- Category accuracy 38.6 %; `continue` predicted 20× against 25 true.
- G1 did not move at all (43.2 % → 43.2 %) while the predictions changed
  substantially: 15 of 20 test items flipped between r2 and r3. The owner
  labels moved individual answers without moving the aggregate.
- G2 improved sharply (27.8 % → 56.0 %) — the variant-B/weight-1 handling works
  as intended, it just misses the 60 % bar.
- G3 is the honest calibration number the plan asked for: the fitted temperature
  reaches ECE 0.075 on its own calibration slice but **0.247 held-out**. The
  confidence number does not generalise; a `confidence_threshold` gate would
  still be meaningless.
- **G4 cannot be measured yet.** All 279 usable shadow labels are in the
  training set (5×), so replaying them gives 94.6 % — in-sample leakage, not a
  gate result. G4 needs labels collected *after* r3 is deployed.

## 5. Verdict

Per the plan's pre-registered rule — "if r3 fails G1–G3, r2 stays the served
artifact; r3 is kept for analysis only" — **r2 remains served**. r3 is not
packaged, the manifest is unchanged and nothing is published.

What the run did establish:

1. The 5 h estimate was wrong; a retrain is a ~40 min job, so iterating is
   cheap and the packet question is closed.
2. Owner labels change individual decisions but not aggregate accuracy on the
   held-out test — consistent with the plan's observation that owner boundaries
   differ from the taxonomy prompt (teachers agree with the owner on ~53 %).
3. The `continue` handling works (recall 27.8 % → 56.0 %) and is one small step
   from its bar.
4. Calibration must be fitted and reported on held-out data; in-sample ECE
   flatters the model by 3×.
