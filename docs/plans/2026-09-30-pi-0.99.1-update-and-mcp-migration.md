**Goal:** Update Pi from 0.87.1 to 0.99.1, migrate the four MCP servers from the pi-mcp-adapter extension to Pi's built-in MCP support, and harden the router for 0.99-specific registry semantics — without breaking MCP in the 0.87.1 sessions that run until the update, and without a window in which an unhardened router runs under 0.99.1. *(Amended 2026-09-30, roborev review round: the second clause did not hold as written — the hardening code is done but the running dist predates it, so an unhardened router IS running under 0.99.1 until the owner restart from the hardening plan's live gate; the Goal survives as the target state, not a description of the interim state.)*

**Architecture:** Pi 0.99.0 ships MCP, codemode, and tool search as built-in extensions. Built-in MCP reads `~/.pi/agent/mcp.json` (global) and `.pi/mcp.json` (trusted projects) in the common `mcpServers` format and names tools `mcp__<server>__<tool>`. The pi-mcp-adapter extension becomes redundant **after** the update — never before, because 0.87.1 has no built-in MCP. The router extension itself is compatible with 0.99.1 (verified 2026-09-30: `tsc --noEmit` 0 errors against the 0.99.1 types, 1071 tests passed, extension loads under the 0.99.1 CLI, groups register, one prompt routed via the `scout` group to an OpenRouter free model).

**Ordering principle:** the router hardening (Task 0) lands **before** the update. Its code is feature-detected and is a no-op on 0.87.1, so the first 0.99.1 session start already runs the hardened router. Only one MCP stack is live at any time: `mcp.json` stays parked until the adapter is uninstalled.

**Tech Stack:** Pi CLI (`pi update`, `pi uninstall`, `pi mcp list`), JSON config files, this repo for the code fixes in Task 0.

### Step 1: Research the re-registration semantics

**Hypothesis (to be verified, not a settled fact):** 0.99.0 changed `pi.registerProvider` so that supplying `models` replaces the provider's models **across chat, image, and classifier operations** (as described in `docs/custom-provider.md` of 0.99.1). If that holds, `registerGroupModels` (`index.ts`, the union path around line 3247) — which re-registers scan-discovered providers (openrouter, mistral, groq, cerebras, xai, deepseek, chutes) with a union of round-tripped **chat** models plus new scan models — would wipe those providers' image models (openrouter) and inherited classifier models (Jev). If the research shows the wipe does not happen, record that here, skip Steps 2–3, and keep only Step 4. The chat-model half of the wipe — pi-registered chat models the scan does not report — is already fixed on 0.87.1: the union now starts from `modelRegistry.getAll()` filtered by provider (roborev job 649 HIGH); Steps 2–3 below cover only the non-chat half.

- Read `docs/custom-provider.md` (model `type` discriminants, `images`/`classifiers` implementation maps) and the `ModelRuntime`/`ModelRegistry` `.d.ts` files.
- Answer: when re-registering a provider with `models` containing round-tripped image/classifier entries (with `type` and `api` fields), do the provider-level implementations reattach, or is an `images`/`classifiers` map required?
- Determine the feature-detection predicate for "pi supports typed models", e.g. `typeof ctx.modelRegistry.getModelsOfType === 'function'`. On 0.87.1 the predicate is false and the current code path runs unchanged.
- Enumerate **every** `registerProvider` call site in `index.ts` and answer the replace question for each, not only for the scan union: group providers (~1642), free-model on-demand (~2331), the scan union (~3248), and the ollama re-registration (~3314) (roborev job 649 LOW).
- Diff the 0.99.1 `ProviderModelConfig`/`Model` `.d.ts` field lists against the round-trip allow-list in the scan union (id, name, api, baseUrl, reasoning, thinkingLevelMap, input, cost, contextWindow, maxTokens, headers, compat): any field 0.99.1 adds to chat models (e.g. `type`, `thinkingLevels`) would be silently lost on re-registration. Extend the allow-list feature-detected (roborev job 649 MEDIUM).

## Rollback — **owner, if a task fails**

**Partial rollback — Task 3 fails (built-in MCP servers do not connect):** no Pi downgrade needed. `pi install npm:pi-mcp-adapter@3.3.0`, restore the adapter config from the Step 5 backup (`cp ~/.pi/agent/mcp-adapter.json.bak ~/.pi/agent/mcp-adapter.json` — it still carries the adapter-specific `"auth": false` that Step 4 may have stripped from `mcp.json`), re-park the built-in config (`mv ~/.pi/agent/mcp.json ~/.pi/agent/mcp.json.pending`), restart Pi. A failed Task 3 is the most likely failure mode and does not require the full downgrade (roborev job 649 MEDIUM).

**Full rollback — Task 2 or Task 4 fails:**

1. `npm i -g @earendil-works/pi-coding-agent@0.87.1` (Pi is installed globally under `~/.npm-global`); verify with `pi --version`.
2. Note: Task 1 Step 2 (`pi update --extensions`) also upgraded the extensions; some may now require ≥ 0.99. Pin/reinstall the versions that worked on 0.87.1 — **best-effort**: Task 1 ran before the Step 0.5 baseline capture existed, so no baseline file was written. Known pins: `@earendil-works/pi-coding-agent@0.87.1` and `pi-mcp-adapter@3.3.0`; reconstruct the remaining extension versions from the npm cache or `~/.pi/agent/npm/package-lock.json` history if a rollback is ever needed (roborev jobs 649/654).
3. Park the built-in config again if it was activated: `mv ~/.pi/agent/mcp.json ~/.pi/agent/mcp.json.pending`.
4. If Task 3 already ran: `pi install npm:pi-mcp-adapter@3.3.0` and restore the adapter config from the Step 5 backup: `cp ~/.pi/agent/mcp-adapter.json.bak ~/.pi/agent/mcp-adapter.json`. Revert any Task 3 Step 6 tool-name edits.
5. Restart every Pi session. The Task 0 router changes stay in place: they are feature-detected no-ops on 0.87.1.
