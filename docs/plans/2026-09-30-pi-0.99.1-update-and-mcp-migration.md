# Pi 0.99.1 Update and Built-in MCP Migration Runbook

> **REQUIRED SUB-SKILL:** Use the executing-plans skill to implement this plan task-by-task.

**Goal:** Update Pi from 0.87.1 to 0.99.1, migrate the four MCP servers from the pi-mcp-adapter extension to Pi's built-in MCP support, and harden the router for one 0.99-specific `registerProvider` semantic — without breaking MCP in the 0.87.1 sessions that run until the update.

**Architecture:** Pi 0.99.0 ships MCP, codemode, and tool search as built-in extensions. Built-in MCP reads `~/.pi/agent/mcp.json` (global) and `.pi/mcp.json` (trusted projects) in the common `mcpServers` format and names tools `mcp__<server>__<tool>`. The pi-mcp-adapter extension becomes redundant **after** the update — never before, because 0.87.1 has no built-in MCP. The router extension itself is compatible with 0.99.1 (verified 2026-09-30: `tsc --noEmit` 0 errors against the 0.99.1 types, 1071 tests passed, extension loads under the 0.99.1 CLI, groups register, one prompt routed via the `scout` group to an OpenRouter free model).

**Tech Stack:** Pi CLI (`pi update`, `pi uninstall`, `pi mcp list`), JSON config files, this repo for the code fix in Task 3.

## Task 3: Fix provider re-registration under 0.99.x — **agent, in this repo, after the update**

**Why:** 0.99.0 changed `pi.registerProvider` semantics: supplying `models` now replaces the provider's models **across chat, image, and classifier operations** (documented in `docs/custom-provider.md` of 0.99.1). `registerGroupModels` (`index.ts`, the union path around line 3247) re-registers scan-discovered providers (openrouter, mistral, groq, cerebras, xai, deepseek, chutes) with a union of round-tripped **chat** models plus new scan models. Under 0.99.x that call would silently wipe those providers' image models (openrouter) and inherited classifier models (Jev).

**Step 1: Research the exact semantics** against the installed 0.99.1:
- Read `docs/custom-provider.md` (model `type` discriminants, `images`/`classifiers` implementation maps) and the `ModelRuntime`/`ModelRegistry` `.d.ts` files.
- Answer: when re-registering a provider with `models` containing round-tripped image/classifier entries (with `type` and `api` fields), do the provider-level implementations reattach, or is an `images`/`classifiers` map required?
- Determine the feature-detection predicate for "pi supports typed models", e.g. `typeof ctx.modelRegistry.getModelsOfType === 'function'`.

**Step 2: Write the failing regression test** (mocked registry exposing `getModelsOfType`): re-registering a provider that owns one image model and one unknown scan model must keep the image model. Prove it red.

**Step 3: Implement.** If implementations reattach on round-trip: include non-chat models from `getModelsOfType('image', provId)` / `getModelsOfType('classifier', provId)` in the union, passing their `type` discriminants. If they do not reattach: **skip re-registration** for providers that own non-chat models, log a router-log warning naming the skipped scan models, and register them only when the provider has none.

**Step 4:** `npx tsc --noEmit` + `npx vitest run` green; commit as `fix: preserve non-chat provider models when re-registering under pi >= 0.99`.
