## Task 1 — Config + Typen

**Files:** `src/types.ts`, `router-config.json`, `test/classifier-laya-config.test.ts`.

**Test (rot, zuerst):**
- Fehlende `classifier_laya`-Config → Stage läuft nicht (bestehende Chain unverändert).
- Config-Shape: `{ enabled: boolean; endpoint?: string; checkpoint: string; timeout_ms?: number; confidence_threshold?: number }` mit Default-Werten:
  - `enabled: false`
  - `endpoint: "http://127.0.0.1:8089"`
  - `checkpoint: null` (erforderlich, wenn `enabled: true`)
  - `timeout_ms: 1500`
  - `confidence_threshold: 0.8`
- Validation: `enabled: true` **ohne** `checkpoint` → Config-Validierungsfehler.
- **ADR-0025 (§9):** Die ausgelieferte `router-config.json` darf **keinen** Checkpoint-Namen enthalten. Default ist `enabled: false`. Der Nutzer trägt den Namen im User-Layer ein.

**Implementierung:**
- Typ in `types.ts` (nahe den bestehenden Classifier-Config-Feldern).
- `ClassifierConfig`-Objekt mit Defaults + Validator.
- `router-config.json` enthält den dokumentierten Block mit `enabled: false`.

**Acceptance:** Suite grün, `tsc --noEmit` sauber, Validator greift bei `enabled: true` ohne `checkpoint`.

## Task 2 — Laya-Client + Probe

**Files:** `src/laya-classifier.ts`, `test/laya-classifier.test.ts`.

**Test (rot, zuerst), gegen einen gestubbten `/classify`:**
- Baut die Frage aus den **9 `VALID_CATEGORIES`** mit den Definitionen aus `src/classification-prompt.ts` (nicht neu erfinden).
- Sendet **eine** Forward-Pass-Frage mit allen 9 Optionen.
- Fehlerkatalog:
  - Connection refused / Timeout → Stage „unavailable", negativer Availability-Marker mit TTL (analog zum 501-Marker).
  - HTTP-Fehler → unavailable.
  - Fehlendes/falsches Antwort-JSON → unavailable, einmalig loggen.
- Probe: keine bloße Ping, sondern eine echte Klassifizierungsaufgabe (bekannter Prompt mit offensichtlicher Kategorie). Probe-Ergebnis steuert die Stage pro Session mit TTL.

**Implementierung:**
- `isLayaAvailable()` / `probeLaya()` (TTL-gesteuert, pro Session).
- `classifyWithLaya(prompt, ctx)`:
  - baut den Request (`prompt` + optionaler `context`-Block wie im Spike).
  - truncaht State nach Task 3.
  - antwortet mit `ClassificationResult` oder `null`.
- Quelle: `laya:<checkpoint>`.
- Timeout über Client (Default 1500 ms) — Laya ist lokal, sollte nicht 15 s blockieren.

**Acceptance:** Suite grün, tsc sauber, Fehlerrouten greifen (unavailable mit TTL).

## Task 3 — State-Truncation

**Files:** `src/laya-classifier.ts` (ergänzend), Tests in `test/laya-classifier.test.ts`.

**Hintergrund:** Das Modell hat ein Kontext-Fenster (512 bzw. 1024 Tokens). Eingabe = `Instruktionen + 9 Optionen + context block + prompt`. Wir senden den **vollen** Prompt, solange er ins Fenster passt; die Truncation ist die Notbremse.

**Test (rot, zuerst) für `truncateState(prompt, ctx, budget)`:**
- Behält Head + Tail (wie Compaction üblich).
- Entfernt zuerst den **context block**, dann den **Prompt-Tail**.
- HINT/Whitespace-Integrität des Prompt-Heads bleibt erhalten.
- Ergebnis bleibt unter `budget` Tokens.
- Budget: **1,024 Tokens** (multilingualer Checkpoint: `encoder/config.json`
  gibt `max_position_embeddings: 8192`, Sliding-Window-Attention
  `local_attention: 128`; Brief sagt 1,024 Tokens). Kopf der Eingabe (9
  Optionen + Instruktionen) verbraucht **408 Tokens**, also bleiben ~600
  Tokens für `context + prompt` bei typischen langen Prompts.
- Da der Router keinen Tokenizer hat: im Client wird die Eingabe
  **zeichengrob** begrenzt (z. B. `prompt + context` auf max. X Zeichen) und
  der Wrapper truncaht token-genau bis `budget`.

**Implementierung:**
- Exportierte `truncateState(prompt, ctx, budget)` (mit einem Tokenizer-Dummy im Test, im Product Code die Zeichen-Grenze).
- Aufruf in `classifyWithLaya` vor dem Request.

**Acceptance:** Suite grün, tsc sauber, Tokenbudget gewahrt.

## Task 4 — Chain-Integration in `classifyPrompt`

**Files:** `src/content-classifier.ts` (Chain-Reihenfolge), erweitert: `test/classifier-fallback-chain.test.ts`.

**Chain-Ordnung:** `HINT-Regex (unchanged) → Laya (local, confidence-gated) → cloud chain (unchanged, opt-in) → Ollama (unchanged) → static keyword fallback (unchanged)`.

**Test (rot, zuerst):**
- Laya **vor** Cloud-Kette und **vor** Ollama.
- `enabled: false` (oder fehlend) → **byte-identische** Chain-Verhalten (bestehende Tests bleiben unverändert grün).
- Laya unavailable / Timeout → transparenter Durchschalten mit der vorhandenen Chain-Narration.
- Niedrige Konfidenz (unter `confidence_threshold`, Default 0,8): **durchschalten** zur nächsten Stufe (nicht `fallback`). Wahl dokumentieren im Test.
- HINT-Eingaben erreichen Laya **nie** (deterministischer Pfad läuft zuerst — pin).

**Implementierung:**
- Stage `classifier_laya` einfügen nach den deterministischen Pfaden, vor der Cloud-Kette.
- `ClassificationResult.reason` aus der Wahrscheinlichkeitsverteilung synthetisieren (Top-2-Kategorien mit Wahrscheinlichkeiten), wenn Laya antwortet.
- Verfügbarkeit prüfen (Task 2), Fallback bei unavailable.

**Acceptance:** Alle bestehenden Chain-Tests unverändert grün; Laya-Tests rot-first grün.

## Implementation log (2026-10-09, Tasks 1–5 on `laya-spike`)

Tasks 1–4 were first landed as `41c1947`..`78d6c2e`, then **redone** on owner
request ("once more, with more verification"): a contract review against the
real wrapper (`spikes/laya-http/server.py`, venv + pinned checkpoint) found
six defects that the unit tests' over-permissive stubs had masked:

- **D1** endpoint: the client POSTed the base URL instead of `base + /classify`
  → `HTTP 404` on every request with the default config.
- **D2** context: sent as flat body fields (the wrapper reads a nested
  `context` object) AND duplicated inside the prompt.
- **D3** truncation: fixed 2×256 char caps ignoring the 1024-token budget and
  the question head; replaced by head-derived budget (`tokens×3` minus the
  prompt surface), head+tail kept.
- **D4** lifecycle: no probe ever ran in production (tests mocked
  `isLayaAvailable()`), no TTL; replaced by a lazy, TTL-gated, single-flight
  `ensureLayaAvailable()`.
- **D5** mode: `active`/`shadow` was never evaluated; now only `active` lets a
  confident, vetted answer decide; `shadow` (validated default) only records
  what Laya would have said.
- **D6** vetting: confident `fallback` and out-of-taxonomy answers were
  returned as classifications; `vetAnswer()` now rejects them.

Commits on `laya-spike` (each red-first with the evidence in the body):
`88df524` (D1–D3, wire tests against the real wrapper contract),
`96b3900` (D4, D6, lifecycle tests with a counting HTTP stub),
`8def033` (D5 + decision-log `laya` observation `{ref, category,
confidence, acted, ms}` + stage/source `laya:<checkpoint>`),
`4f22dfa` (Task 5: `/router status` Laya line with the honest three-state
availability `ok | down | unknown` — "not probed yet" is not a failure — and
Laya in the Chain line only in `active` mode).

Non-vacuity: tests that were green at birth (already-correct behavior) were
mutation-checked; two surviving mutants led to new tests
(failure-after-healthy-probe swallowed; unset `mode` shown as shadow).

**End-to-end verification** (no mocks; real chain → real HTTP wrapper → real
MLX model), repeatable via `scripts/laya-e2e.ts`:

- active: the design prompt decides via `laya:<checkpoint>` (0.98); German
  design at 0.69 and `code_simple` cases correctly stay below the threshold
  and fall through.
- shadow: identical Laya answers logged with `acted: false`, routing
  unchanged (byte-identical chain).
- dead endpoint: one failed probe, clean fall-through, no hammering
  (TTL-gated `down`).
- wrapper killed mid-session: next request falls through, state `down`,
  subsequent requests add 0 ms.
