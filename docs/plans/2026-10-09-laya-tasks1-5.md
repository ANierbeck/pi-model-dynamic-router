## Task 3 — State truncation

**Files:** `src/laya-classifier.ts` (additive), tests in `test/laya-classifier.test.ts`.

**Background:** the model has a context window (512 resp. 1024 tokens). Input = `instructions + 9 options + context block + prompt`. We send the **full** prompt as long as it fits; truncation is the emergency brake.

**Test (red, first) for `truncateState(prompt, ctx, budget)`:**
- Keeps head + tail (as compaction usually does).
- Removes the **context block** first, then the **prompt tail**.
- HINT/whitespace integrity of the prompt head is preserved.
- Result stays under `budget` tokens.
- Budget: **1,024 tokens** (multilingual checkpoint: `encoder/config.json` gives `max_position_embeddings: 8192`, sliding-window attention `local_attention: 128`; the brief says 1,024 tokens). The input head (9 options + instructions) consumes **408 tokens**, so ~600 tokens remain for `context + prompt` on typically long prompts.
- Since the router has no tokenizer: in the client the input is limited **coarsely by characters** (e.g. `prompt + context` to max. X chars) and the wrapper truncates token-exactly to `budget`.

**Implementation:**
- Exported `truncateState(prompt, ctx, budget)` (with a tokenizer dummy in the test, the character cap in product code).
- Called in `classifyWithLaya` before the request.

**Acceptance:** suite green, tsc clean, token budget respected.

**Chain order:** `HINT regex (unchanged) → Laya (local, confidence-gated) → cloud chain (unchanged, opt-in) → Ollama (unchanged) → static keyword fallback (unchanged)`.

**Test (red, first):**

**Implementation:**

- Check availability (Task 2), fall back when unavailable.

## Implementation log (2026-10-09, Tasks 1–5 on `laya-spike`)

Tasks 1–4 were first landed as `41c1947`..`78d6c2e`, then **redone** on owner
request ("once more, with more verification"): a contract review against the
real wrapper (`spikes/laya-http/server.py`, venv + pinned checkpoint) found
six defects that the unit tests' over-permissive stubs had masked:

- **D1** endpoint: the client POSTed the base URL instead of `base + /classify`
  → `HTTP 404` on every request with the default config.
- **D2** context: sent as flat body fields (the wrapper reads a nested
  `context` object) AND duplicated inside the prompt.
- **D3** truncation: fixed 2×256 char caps ignoring the 1024-token budget and
  the question head; replaced by head-derived budget (`tokens×3` minus the
  prompt surface), head+tail kept.
- **D4** lifecycle: no probe ever ran in production (tests mocked
  `isLayaAvailable()`), no TTL; replaced by a lazy, TTL-gated, single-flight
  `ensureLayaAvailable()`.
- **D5** mode: `active`/`shadow` was never evaluated; now only `active` lets a
  confident, vetted answer decide; `shadow` (validated default) only records
  what Laya would have said.
- **D6** vetting: confident `fallback` and out-of-taxonomy answers were
  returned as classifications; `vetAnswer()` now rejects them.

Commits on `laya-spike` (each red-first with the evidence in the body):
`88df524` (D1–D3, wire tests against the real wrapper contract),
`96b3900` (D4, D6, lifecycle tests with a counting HTTP stub),
`8def033` (D5 + decision-log `laya` observation `{ref, category,
confidence, acted, ms}` + stage/source `laya:<checkpoint>`),
`4f22dfa` (Task 5: `/router status` Laya line with the honest three-state
availability `ok | down | unknown` — "not probed yet" is not a failure — and
Laya in the Chain line only in `active` mode).

Non-vacuity: tests that were green at birth (already-correct behavior) were
mutation-checked; two surviving mutants led to new tests
(failure-after-healthy-probe swallowed; unset `mode` shown as shadow).

**End-to-end verification** (no mocks; real chain → real HTTP wrapper → real
MLX model), repeatable via `scripts/laya-e2e.ts`:

- active: the design prompt decides via `laya:<checkpoint>` (0.98); German
  design at 0.69 and `code_simple` cases correctly stay below the threshold
  and fall through.
- shadow: identical Laya answers logged with `acted: false`, routing
  unchanged (byte-identical chain).
- dead endpoint: one failed probe, clean fall-through, no hammering
  (TTL-gated `down`).
- wrapper killed mid-session: next request falls through, state `down`,
  subsequent requests add 0 ms.
